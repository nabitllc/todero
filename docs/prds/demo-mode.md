## 1. Overview

### Problem Statement
The public `/demo` is a hand-copied fixture of one screen. It cannot be clicked and it drifts the day the product changes. A stranger who reads "or see a bolt →" on the landing gets a picture, not the product.

### Target Users
A stranger from the landing who wants to know what Todero is before joining the waitlist. Secondary: Michael, reviewing the product on a phone without a running instance.

### Success Metrics
- A stranger can, without instructions and without a dead end: create and move a task, comment and @ an agent and get a reply, approve or reject an approval, hire an agent.
- Every screen in the demo is the real `local/ui` component. Zero demo-only UI.
- The demo cannot fall behind the product silently: a CI job builds it and walks it on every PR.
- Nothing leaves the browser. No model runs. Zero cost per visitor.

## 2. User Stories

- **As a** stranger, **I want** to click around a working Todero **so that** I believe the landing's claim before I give my email.
- **As a** stranger, **I want** to be told plainly that it is a demo of an invented company **so that** I don't think my edits went somewhere or the data is someone's real work.
- **As** Michael, **I want** the demo to be the product itself **so that** it stays true "however Todero works, now and in the future."
- **As** a maintainer, **I want** a schema change to break the demo build **so that** drift is caught by CI, never by a visitor.

## 3. Scope

### In Scope
- A `demo` build mode of `local/ui` served at `todero.vercel.app/demo`.
- Fetch-level fake backend (MSW, browser service worker) covering the 52 recorded read endpoints, the two automatic POSTs, and the write endpoints for the four interactions.
- Seed: one invented company, five agents by role, one goal named "Bolt 14" (24h window in its description), eight tasks across statuses, one pending approval, activity, one canned agent run transcript.
- In-memory store persisted to `sessionStorage`; Reset.
- One-line banner: "Demo — an invented company, nothing leaves your browser · Reset".
- Entry: `/demo` lands on the task board of the seeded company.
- Drift gate in CI.
- Landing "or see a bolt →" points at the entry.

### Out of Scope
- A bolt feature in the product (sprint object, board, timer). The demo shows the product as it is; "bolt" is the seeded goal's name.
- Running any model. Agent replies and runs are canned.
- Plugin-gated and flag-gated screens (`apps`, `cases`, `board-chat` redirected on the reference instance). They render whatever the real UI renders with empty data.
- Auth, invites, members, sign-up. Untouched, per the license/NOTICE constraint.
- Analytics on demo usage.

### Dependencies
- `local/ui` builds standalone (`vite build`) — true today.
- `local/packages/shared` response types — exist.
- Vercel serves static files from the Next site's `public/` — true today.

## 4. Technical Specification

### 4.1 File Structure
```
local/ui/src/demo/
  index.ts                 entry guard: starts MSW when import.meta.env.VITE_TODERO_DEMO === "1"
  store.ts                 in-memory state + sessionStorage persistence + reset()
  seed.ts                  the invented company (typed against @todero/shared)
  handlers/
    shell.ts               the 21 endpoints every screen fires
    companies.ts  agents.ts  issues.ts  approvals.ts  activity.ts
    goals.ts  projects.ts  routines.ts  inbox.ts  org.ts  settings.ts  vault.ts
  socket.ts                fake WebSocket for /events/ws, emits from the store
  transcript.ts            canned agent replies and one run, from ui/src/fixtures/runTranscriptFixtures.ts
  DemoBanner.tsx           the one line + Reset
  unhandled.ts             throws visibly on any /api request without a handler
local/ui/vite.config.ts    base "/demo/" under demo mode
local/ui/src/main.tsx      demo guard before providers; Sentry, SW updates, plugin bridge off in demo
local/ui/public/mockServiceWorker.js   generated by msw
app/next.config.js         rewrite /demo/:path* → /demo/index.html; /demo → /demo/
app/demo/*                 deleted (the canned fixture)
scripts/build-demo.mjs     builds local/ui in demo mode into public/demo/
.github/workflows/demo.yml the drift gate
```

### 4.2 Data Model
The seed uses the product's own types from `@todero/shared`: `Company`, `Agent`, `Issue`, `Approval`, `Goal`, `Project`, `Routine`, `ActivityEvent`, `Comment`, `HeartbeatRun`. No demo-only types. The store is a plain object keyed by collection, serialized to `sessionStorage["todero-demo"]` on every mutation; `reset()` reloads the seed.

Invented company: **Kelp Works** — prefix `KELP`, mission "Ship the docs site for a local-first app." Agents: Lead, Research, Build, Test, Write. Tasks KELP-1…KELP-8 across Backlog / Todo / In Progress / In Review / Done. One approval pending: "Hire a Support agent." Goal: "Bolt 14 — 24 hours to launch the docs site."

### 4.3 Authorization
None. The demo has no server and no accounts. `GET /api/auth/get-session` and `/companies/:id/:id/me` return a fixed demo user with board role so every real UI gate opens. Nothing in `local/server` changes.

### 4.4 API — the fake
- **Reads (52 from the spike):** handlers return from the store, typed as the product's response types.
- **Automatic POSTs:** `POST /issues/:id/read` → 204; `POST /todero/vault/recommended/ensure` → `{ ok: true }` with a recommended-brain stub.
- **Writes for the four interactions (to be recorded in slice 1, ≈15–25):** create issue, update issue (status, assignee), add comment, resolve approval, create agent. Each mutates the store, persists, and pushes an event through the fake socket so the real live-update path re-renders.
- **Unhandled:** any `/api` request with no handler resolves to HTTP 599 with body `{ error: "demo: unhandled <METHOD> <path>" }` and logs a console error. The UI's normal error state shows it. This is the drift alarm.

### 4.5 External APIs & Async Handling
No external calls. "Agent replies" are asynchronous by design: a comment that @-mentions an agent schedules a canned reply 1.5–3 s later through the fake socket, so the real thinking/streaming states render. `prefers-reduced-motion` does not change timing; it is data, not animation.

## 5. UI/UX Specification

### 5.1 User Flow
Landing → "or see a bolt →" → `/demo` (task board of Kelp Works, one task In Progress with an agent run visible) → click a task → comment "@Build what's left?" → reply arrives → Approvals → approve "Hire a Support agent" → Agents → the new agent is listed → Reset.

### 5.2 Visual Design
The product's own design. The only new surface is the banner: one line, `--wi-*` tokens from the work-item system, no card, no modal, no dismiss (Reset is the only control). Consumer benchmark for the banner: Vercel's preview-deployment toolbar — quiet, always there.

### 5.3 Layout
Banner pinned to the top of the app shell, 2.5rem, above the real header. Nothing else moves.

### 5.4 Components
`DemoBanner` (new). Everything else is existing product UI.

### 5.5 States
- Loading: the product's own skeletons — handlers add 80–200 ms latency so they actually show.
- Empty: real empty states for collections the seed leaves empty.
- Error: the product's own error states; unhandled endpoints surface there.
- Success: the product's own toasts.

### 5.6 Accessibility
Inherits the product's. The banner is a `role="status"` region with a 44×44 Reset button and visible focus.

## 6. Edge Cases & Error Handling
- `sessionStorage` unavailable (private mode): store runs in memory, Reset still works, a console note explains.
- Storage from an older seed version: `seed.version` mismatch → reset automatically.
- Deep link to a task that the visitor deleted: real 404 state.
- Service worker fails to register (older browser): fall back to a `fetch` shim in the same tab; same handlers.
- Visitor opens two tabs: each tab has its own session; that is acceptable and stated nowhere — they are separate demos.
- The real app's `startServiceWorkerUpdates` is off in demo mode so it never fights the MSW worker.

## 7. Testing Requirements
### Unit
- Store: every mutation persists and `reset()` restores the seed.
- Handlers: type-check against `@todero/shared`; a response shape drift fails `tsc`.
### E2E (Playwright, demo build)
- Walk the 16 screens from the spike; assert zero unhandled-endpoint errors and zero console errors.
- The four interactions end to end.
- Reset restores KELP-1…8.
### Manual
- Phone at 375: banner does not cover the header; the four interactions with a thumb.

## 8. Implementation Plan
1. **Seam (1.5 d):** record write endpoints for the four interactions on a throwaway company; demo guard in `main.tsx`; MSW; fake socket; shell handlers; unhandled alarm. Exit: dashboard boots with seed.
2. **Seed and handlers (3 d):** full seed; the 31 remaining reads; the writes; canned replies and run; `sessionStorage` + Reset; banner. Exit: the five-step user flow works locally.
3. **Hosting (1 d):** Vite `base`, build script into `public/demo/`, Next rewrite, delete `app/demo/*`. Exit: `todero.vercel.app/demo/KELP/issues` deep-links.
4. **Drift gate (1 d):** CI workflow builds the demo and runs the E2E walk on every PR. Exit: a deliberately broken handler fails CI.
5. **Landing (0.25 d):** link target; regenerate the landing's canned board from the seed so both stay one truth.

Order note: 3 before 4 because the gate tests the hosted build layout; 5 last because the seed must be final.
