# Retrospective: one pass, while the work is fresh

After wrap-up, before you close the task, run this once. Look back at what went wrong and what you fixed. The retrospective is not finished until one concrete thing changes.

## Three sections

**What went wrong:** List problems encountered, how they were discovered, and what finally fixed them.

**What stayed:** Techniques that worked and should be kept. Patterns the skills got right.

**One thing to change:** Pick one skill that should be edited, or one missing skill to propose. Name it. Name the line that should change, and one sentence of why.

## Tone

Write as if explaining to someone who will do the work: specific error messages, exact file paths, what the failure looked like. Be honest about mistakes — they are the best teachers.

## Format

```
## Retrospective

### What went wrong
- [problem]: [what happened] -> [what fixed it]
- ...

### What stayed
- [technique]: [description]
- ...

### One thing to change
Skill: [name]. Line: [quote the line]. Why: [one sentence].
```

## What Todero changed

Kept from vault sources: never edit skills directly (write proposals only); the format shape (what went wrong, techniques worth keeping, the closing rule that something concrete must change).

Changed: cadence. The vault reviews weekly; Todero runs the retrospective once, right after wrap-up, while the work is in memory. The output is at most three proposals per run, each with the line that should change and one sentence of why. The one-concrete-thing rule is the gate: if the retrospective cannot name one change, there is no retrospective file.
